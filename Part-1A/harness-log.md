# SpendWise Harness Log

Single record of how the independent harness was built, what each run produced, every failure, every repair, and every human decision. Nothing in this file is filled in before the thing it describes has really happened. A value that has not been produced yet is `PENDING` or `NOT RUN`.

## 1. Rules of engagement

- **Independence.** The harness (`harness/`) is written from `spec.md`, `data-model.md`, and `contracts/api.md` before any application code exists. It does not import from `backend/` and never reads application output to decide an expected value.
- **Read-only for the coding agent.** The coding agent never creates, modifies, or deletes anything under `harness/` or `evidence/`, and never edits this file. The harness changes after the freeze (T016) only through a harness-defect fix by the harness author that a human approved (T077).
- **Expected values come from the spec only.** `harness/cases/*.json` is generated by `harness/tools/build_cases.py`, which holds a small reference model of the spec documents (Decimal and integer cents, no application code). A human reviews the generated JSON against the spec at T016, not against the application.
- **Status vocabulary.** A check is exactly one of:
  - `PASS`: executed, not vacuous, and met its criterion (exit code 0, and tests ran, or a coverage percentage was reported, or an API case was compared, or files were scanned).
  - `FAIL`: executed and did not meet its criterion, or exited 0 without doing anything meaningful, or pytest exit code 5 (no tests collected).
  - `ERROR`: the check or the harness itself broke, so there is no verdict on the application: the command could not start, a harness exception, a timeout, a server that was started but never answered, pytest exit code 2, 3, or 4, ruff exit code 2, or a scanner exit code other than 0, 1, or 3.
  - `NOT RUN`: the subject does not exist yet or a prerequisite check did not run (an unmet precondition), or a scan examined zero files (scanner exit code 3). The command is not executed and the exit code is recorded as `n/a`.
  - `PENDING`: a human check that has not been done yet.
- **Required versus supplementary.** Every check is tagged `required` or `supplementary` (supplementary: the HTTP timing case `API-timing`, the `G9-secret-patterns` scan on the source tree, `evidence/README.md`, and an automated SC-010 Playwright run). Results report the two kinds separately and a supplementary result never offsets a required one.
- **No fabricated results.** A result is written only after the check ran and its real exit code and output were captured in an evidence folder.
- **Initial evidence is immutable.** `evidence/` run folders are never overwritten or deleted. The harness refuses to write into a non-empty folder.
- **Harness defects.** If a check misbehaves because of the harness (not the application), the harness author proposes a fix, a human approves it (T077 after the freeze), the change and the reason are logged in section 3, and a new complete run is recorded in a new folder. The old run is kept and never edited.
- **Secret-safe evidence.** Evidence never includes `.env` or `.env.*` files (only `.env.example`), `*.log`, `*.db`, `node_modules`, `dist`, `.venv`, `__pycache__`, `.pytest_cache`, or coverage output. The environment record lists tool versions only. The scanner reports file, line, and rule name only, never the matched text.

### Harness author notes (recorded at T009 to T014, before the first official run)

- The harness author is the same assistant session that performed Phase 1 setup. The independence safeguard is the human review at T016 and the fact that the application code did not exist when the harness was written. The assistant that builds the application from Phase 3 onward must not edit `harness/` or `evidence/`.
- Interpretation of T013 preconditions: the `G9-secret-patterns` scan on the source tree is `NOT RUN` until a SpendWise Python source file under `backend/app/` (not an empty `__init__.py`) or `frontend/src/api/client.ts` exists, because the Phase 1 tooling files and the stock Vite template would otherwise be "files to examine" and T015 expects `NOT RUN` on the empty baseline. The `float` scan examines only non-empty files, so empty `__init__.py` files do not count as something to examine.
- The black-box timing case runs as its own phase (`--phase timing`) and its own check `API-timing`, so a timing problem cannot fail the required API checks. It records elapsed milliseconds only and has no time limit.
- `run_api_checks.py --phase all` runs write, verify, and timing against one running server without a restart; the harness runner uses `write`, a restart, then `verify` and `timing`.
- `frontend` lint uses `oxlint --deny-warnings` (the current Vite template's linter), not ESLint; see tasks.md T006.
- Author-side checks before this log was finished (not evidence, not recorded in the run register): the harness scripts were parsed for syntax errors, the self-test and a baseline dry run were executed into throwaway folders under the user's temp directory (deleted afterwards), the scanners were exercised on a throwaway sample, and the API runner was exercised against an unreachable address and a one-endpoint stub. The official Run 0 (T015) is run by the operator into `evidence/repairs/`.
