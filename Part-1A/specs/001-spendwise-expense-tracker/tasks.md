# Tasks: SpendWise Personal Expense Tracker

**Input**: Design documents from `/specs/001-spendwise-expense-tracker/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/api.md](contracts/api.md), [quickstart.md](quickstart.md), `.specify/memory/constitution.md` v1.1.0

**Tests**: Included. The constitution (Principle V, gates G4 to G10) and the plan's traceability table require automated tests. Every test task comes before the implementation task it covers.

**Organization**: Tasks are grouped by user story (US1 to US4) so each story can be built, tested, and demonstrated on its own. An independent harness (Phase 2) is built before any application code, and its evaluation and repair loop (Phase 9) runs after the first complete generation. Deadline: 2026-11-15.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: US1 Record and manage expenses, US2 Categorize and filter, US3 Monthly budget, US4 Dashboard
- **[HUMAN]**: A person must perform or decide this; the coding agent must not do it, tick it, or invent its outcome
- All paths are relative to the repository root `Part-1A`

## Path Conventions

- Backend: `backend/app/` (code), `backend/tests/unit/` and `backend/tests/api/` (tests)
- Frontend: `frontend/src/`, tests next to the file they cover as `*.test.ts(x)`
- Harness: `harness/`, `harness-log.md`; evidence: `evidence/initial-generation/`, `evidence/repairs/`, `evidence/snapshots/`, `evidence/final-generation/`
- Package manager for the frontend is **Yarn 1.22 (classic)**: `yarn install --frozen-lockfile`, `yarn dev`, `yarn build`, `yarn lint`, `yarn test`; `yarn.lock` is committed
- Reference date for all automated tests and the harness: `2026-11-12`

## Roles

- **Harness author**: builds the harness and the evidence folder structure before the freeze, in T001 (the `harness/cases` and `evidence/` folders) and T009 to T014, working only from spec.md, data-model.md, and contracts/api.md (no application code exists yet). After the freeze (T016) the harness changes only through a harness-defect fix that a human approved at T077. A harness defect found by T015 before the freeze is also fixed by the harness author, never by the operator or the coding agent.
- **Setup (T002 to T007)**: prepares the project tooling and files: `backend/pyproject.toml`, the requirements files, `.gitignore` and `backend/.env.example`, the virtual environment, the `frontend/` scaffold, and `README.md`. It is done by whoever prepares the project (the human or the coding agent). These tasks create no SpendWise application code and never create, modify, or delete anything under `harness/` or `evidence/`. The `backend/` folder skeleton in T001 belongs to setup too.
- **Coding agent**: implements and repairs the application from T017 onward (and the repair part of T079). It must never create, modify, or delete any file under `harness/` or `evidence/`, and it does not edit `harness-log.md`.
- **Independent operator** (written "operator" in the tasks): the human, or the harness scripts the human runs, and never the coding agent. From T015 onward it runs the harness, freezes and records evidence, and generates snapshots, change lists, diffs, repair prompts, and repair summaries (T015, T074 to T082, T086).
- **Human**: performs the `[HUMAN]` tasks and decisions (T008, T016, T077, T083 to T085).

## Evidence rules (apply to every task)

- A check, gate, or test is reported as passing only after it was executed and its real exit code and output were captured. Never write a result before running the check.
- Statuses are exactly `PASS` (executed, not vacuous, and met its criterion), `FAIL` (executed and did not meet it, or ran nothing meaningful), `ERROR` (the check or the harness itself broke, so there is no verdict on the application), `NOT RUN` (its subject does not exist yet or a prerequisite check did not run; the command was not executed), or `PENDING` (a human check not yet done). The mapping from exit codes to statuses is defined in T013.
- The prohibition on touching the harness and the evidence applies to the coding agent: it never creates, modifies, or deletes any file under `harness/` or `evidence/`. The harness author creates the harness and the evidence folder structure in T001 and T009 to T014 before the freeze (T016), and afterwards only through a human-approved harness-defect fix (T077). Evidence (run folders, snapshots, manifests, change lists, diffs, repair prompts, and repair summaries) is generated only by the independent operator: the harness runner, or the human running the named commands. The operator never modifies or deletes an existing evidence file after the harness is frozen (T016); it only adds the new files that T015, T074, T075 to T082, and T086 describe.
- **Secret-safe evidence scope**: snapshots, manifests, change lists, diffs, and run folders never include or quote `.env` or `.env.*` files (only `.env.example` is allowed), `*.log` files including `yarn-error.log`, `*.db` files, `node_modules`, `dist`, `.venv`, `__pycache__`, `.pytest_cache`, or coverage output. Every tool that copies or prints file content (snapshot copy, manifest, diff, stdout capture) applies the same exclusions, the environment record lists tool versions only and never environment variable values, and the secret scanner still scans `.env*` files in the working tree but reports only file path, line number, and pattern name, never the matched text. After a snapshot or run folder is written, the scanner is run over it, and any finding is reported (redacted) to the human before the folder is marked read-only or used.
- Initial results are never overwritten or deleted.

## Essential versus supplementary work

- **Essential** work meets a compulsory assignment requirement: every functional requirement and success criterion in spec.md, constitution gates G1 to G10, the tests in the plan's traceability table, the independent harness with initial-generation and final-generation evidence, `harness-log.md`, and the human checkpoints. Every task is essential unless it is marked `(supplementary)`.
- **Supplementary** work is extra evidence or convenience. It never replaces or offsets an essential check, it is the first thing dropped if time runs out, and a dropped item is recorded in `harness-log.md` as `NOT RUN`, not as passed. Supplementary items: the HTTP timing case in T011, the `secret-patterns` scan in T012, `evidence/README.md` (T014; no other task depends on it), and an automated Playwright version of the SC-010 walkthrough (T084). Repair rounds after the first (T078 to T080) are essential only while genuine failures remain.

## Performance checks are kept separate

| Check | What it measures | Limit | Source | Kind |
|-------|------------------|-------|--------|------|
| SC-005a, manual (T083) | Whole main screen: navigation start until list and dashboard are visible, 1,000 expenses, cache disabled, 5 runs | Every run within 2 seconds | spec.md SC-005 | Essential |
| SC-005b, automated in process (T064) | Server work only for list-all and monthly summary, no browser, no network, after one warm-up call | Each under 500 ms | spec.md SC-005 | Essential |
| Harness HTTP timing (T011) | Elapsed milliseconds of list-all and monthly summary over local HTTP with 1,000 expenses | No limit; recorded only | None | Supplementary |

The spec and plan define no HTTP-level time limit, so the harness never passes or fails a check on HTTP time.
